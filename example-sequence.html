1 Introduction

Each sequence diagram shows one use case scenario as messages between objects over time. They turn the steps of the use case descriptions into operations, which then appear in the class diagram.

  • Participants follow the boundary – control – entity pattern: the actor talks only to a screen, the screen to a controller, and the controller to the entity objects.
  • Synchronous calls have filled arrowheads; replies are dashed; asynchronous messages have open arrowheads.
  • Messages are numbered in order. The communication diagram uses the same numbers, so the two can be compared line by line.

4 The same scenario as a communication diagram

The sequence diagram makes the order and the alternatives easy to follow; the communication diagram makes the links between objects easy to see — here, that the controller is the only object that talks to every entity. Replies are not drawn on a communication diagram.

5 SD-02 Pay tuition (UC-08)

  • Message 9 is asynchronous. The student pays on the gateway’s own page; the gateway then calls the USMS back, possibly seconds later.
  • Message 10 is a self-call. The controller checks the gateway’s signature before believing the status (NFR-02 and the security note in UC-08 extension 6a).
  • The alt guard covers every outcome. Success records the payment once; failure or no status within 60 seconds shows a retry (FR-21).
  • sendReceipt is asynchronous, so a slow email service never delays the receipt on screen.

7 Checks

  • ✓ Each diagram follows one use case; its first message is the actor’s action from step 1 of the description.
  • ✓ Every alt fragment has guards that together cover all outcomes.
  • ✓ The actor talks only to boundary objects.
  • ✓ Every message is an operation of the receiving class in the class diagram.
  • ✓ The communication diagram uses the same message numbers as SD-01.
