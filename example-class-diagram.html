1 Introduction

The class diagram is the static structure of the USMS: the things the system must remember, their attributes and operations, and how they are related. The domain classes (section 3) also define the database tables; the design classes (section 7) show how the payment code is organised.

2 Finding the classes

“A student enrolls in a section of a course during the registration window of a semester. Each course may have prerequisites. A faculty member enters marks for the sections they teach, and the registrar office publishes the results. The student pays a tuition fee, calculated from the credits, through the payment gateway and receives a receipt. Every change to a student record is logged.”

6 Design decisions

  • Enrollment is a class, not a plain many-to-many line between Student and Section, because the link itself carries data: status, marks and grade.
  • Grades live in Enrollment. A grade belongs to one student in one section, not to the student or the course alone. GPA and CGPA are calculated, not stored (FR-16).
  • Seats left is an operation, not an attribute. It is capacity minus the active enrollments, as in the DFD, so it can never be out of date.
  • Prerequisites are a reflexive association on Course. Section.prerequisites() simply asks its course, so the controller only talks to the section.
  • User is abstract and holds what all accounts share, so log-in rules (FR-06 lockout) are written once.
  • Composition only where the part cannot outlive the whole: a Payment without its FeeInvoice makes no sense; a Section can exist before any student enrolls, so Section — Enrollment is a plain association.

7 Design classes for online payment

  • PaymentController calls the gateway only through the «interface» PaymentGateway. A test version (a fake gateway) can replace GatewayAdapter in tests, and another provider can be added later without changing the controller.
  • The dashed arrow with a hollow triangle is realization: GatewayAdapter implements every operation of the interface.
  • The «create» dependency shows that the controller creates Payment objects (SD-02, message 11) but does not keep them.
